# 分区与共享

全局化后写入门的核心判据：不只判「值不值得记」，先判「**记到哪一层**」。ingest skill 每次写入前按本文件执行。

## 三级写入门

| 层 | 判据 | 例 | 不属于 |
|---|---|---|---|
| **项目内**（该项目自己的 `AGENTS.md` / `docs/` / `.memory/`，展开见下「与 `.memory/` 的分工」） | 只对该项目成立、离开项目无意义的事实 | 某服务的部署拓扑、构建命令、代码约定、对该仓的工作偏好 | 换个项目还会用到的方法论 |
| **`wiki/projects/<项目>/`** | 与单项目绑定、但跨会话/跨机器仍需要的结论 | 该项目的排障案例、架构决策记录、演进史 | 项目一关就作废的临时状态 |
| **`wiki/` 公共层**（concepts / entities / operations / decisions / risks） | 跨项目可复用的概念、方法、决策、人与外部系统实体 | 「ICMP mtr 测不到 TCP 层丢包」、某外部系统的接入要点 | 单项目专属细节 |

配套规则：

- **同一事实不两写**。项目内已有的，`config/registry.md` 登记路径、wiki 页引用，不复制。
- 一次性调试命令、未确认猜测、纯聊天内容、无复用价值的过程不写。
- 证据不足但值得跟踪的写 `wiki/risks/`，标「待核验」。
- 学习类内容进 `wiki/learning/`（见 learn skill）；讲义等生成物进 `outputs/learning/`。

## 与 `.memory/` 的分工

`.memory/`（本仓及任何接了 skill `agent-memory-setup` 的仓库都有）和 wiki 都存跨会话内容。两者不按「项目内 / 跨项目」分，那条轴上 `.memory/` 与 `wiki/projects/` 完全重合；判据是**这条信息是「怎么跟我干活」还是「世界是什么样」**：

| | `.memory/`（工作方式层） | wiki（知识层） |
|---|---|---|
| 回答的问题 | 在这个仓库里应该怎么做事 | 某个对象、机制、决策、故障为什么是这样 |
| 形态 | 一条一事实，祈使句，无推理链 | 有来源、最后核验、被否方案的事实页 |
| 生命周期 | 仓库删了就没意义 | 仓库删了仍有价值 |
| 读取 | 每次会话开始自动读索引 | 排障、设计、学习时按需 query |
| 写入 | 用户给偏好、纠正做法、说出约束的当下 | 任务收口时 ingest |
| 谁读 | 该仓的所有 Agent | 装了本工作台 skill 的会话 |

`.memory/` 四个 type 的落位：`user`、`feedback`、`reference` 只在记忆；`project` 只放**约束与状态**（「目标是 X、不能动 Y 接口、Z 待拍板」），带推理链或被否方案的结论不进记忆。纠正背后的机制若跨项目成立，机制进 `concepts/`，记忆里只留一句结论加指针；被指向的外部系统要写接入要点，那是 `entities/`。

**项目内的四个家**（三级写入门第一行的展开）：

| 家 | 收什么 | 不收什么 |
|---|---|---|
| 仓内 `AGENTS.md` | 对所有人都成立的项目规则 | 个人偏好 |
| 仓内 `docs/`（specs、plans、ADR） | 该项目**当前**的设计结论及被否方案 | 已过时的历史 |
| 仓内 `.memory/` | 偏好、纠正、约束、指针 | 任何需要来源和核验的事实 |
| `wiki/projects/<项目>/` | 该项目的**排障案例与演进史**；没有代码仓的工作对象（服务器、客户、系统）的全部结论 | 仓内 `docs/` 已有的当前设计，只放链接 |

四条机械规则：

1. **同一事实一个家，另一边只放指针。** `.memory/` 的 `reference` 条目可以指 wiki 页；wiki 页通过 `config/registry.md` 登记名指仓库路径。都不复制对方正文。
2. **写入前一问**「离开这个仓库还有意义吗」：没有，进 `.memory/`；有，再问「做事方式还是事实结论」。两问后仍犹豫，是两条信息混在一起，拆开。
3. **没有 `.memory/` 的仓库不降级到 wiki。** 偏好走工具自带记忆；不把偏好塞进 `wiki/projects/` 当替代品。
4. **收口可以同时写两边，但必须是两条不同的信息。**「以后先查 X 再查 Y」是 `feedback` 进记忆，「根因是 Z」是结论进 `operations/`。

## 专项实例的读法

专项工作台（未被 `~/.llm-wiki` 指向、直接进入目录使用的实例）沿用同一套三级门，判据中的「项目」读作域内的**工作对象**（系统、代码库、客户等）：只对某工作对象成立的事实留在其自己的仓库或文档；与单个工作对象绑定但跨会话需要的进 `wiki/projects/<工作对象>/`；域内跨对象复用的进公共层。私有区与凭证红线两种形态完全一致。

## 私有区

`wiki/private/` 被 `.gitignore` 排除，物理不出本机。**必须**写入私有区的内容：

- 对他人的评价、绩效、薪酬信息；
- 未公开的组织事项；
- 其他你不愿意出现在任何远端或团队编译里的内容。

私有区不是凭证保管处——密码、token、私钥、kubeconfig、完整连接串**任何分区都不收**，一律走本机钥匙串或凭据文件，wiki 里只登记「存在哪」。

## 可共享边界

`wiki/private/` 之外的全部内容默认可共享：会被 `sync.sh` 推到你的个人远端，也可能被团队编译层拉取。写公共层与项目分区时保持这个预期；拿不准就先写 private，之后再迁出。

## 敏感域扩展

采集类域扩展（聊天记录、项目管理数据等）在 `config/registry.md` 登记时必须标注敏感级别；标「受限」的域，其数据与分析结论留在域扩展自己的仓库，本仓 index 只挂入口行、不下钻内容。
